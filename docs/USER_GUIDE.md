# Forge ML user guide

Forge ML is a desktop scientific IDE for Rust machine-learning projects. Open a Cargo project, edit Rust scripts or `//# %%` notebooks, and run cells in the persistent Evcxr console.

## Keyboard workflow

- `Ctrl+Shift+P`: open the searchable command palette.
- `F6`: move to the next right-side inspector pane.
- `Ctrl+1`: return to Variables.
- `Shift+Enter`: run the current cell.
- `Ctrl+Shift+Enter`: run all cells.
- `Ctrl+S`: save; `Ctrl+N`: new file.
- `Ctrl+F`: find in the active file; `Ctrl+Shift+F`: search the project.
- `Ctrl+Space`: request rust-analyzer completion.

The command palette accepts words from a command name or its shortcut. Use Up/Down, Enter, and Escape without reaching for the mouse.

## Accessibility

Settings offers light/dark themes, a 10–24 px editor font, high contrast, reduced motion, and caret blinking. Reduced motion disables the custom blinking caret. Execution, diagnostics, Git state, and cells use text or symbols in addition to color.

## Data and experiments

Import CSV, TSV, JSON Lines, Parquet, or Arrow IPC from the Data pane or Tools menu. Parsing runs in the background, reports the active path and decoded row count, and opens a successful import in the adjustable lower-right viewer only after Arrow construction and quality preparation finish. Interactive imports are limited to 512 MiB on disk, one million rows, 10,000 columns, 512 MiB of decoded cell text, and 16 MiB per cell or JSON line. Parquet is decoded in bounded batches and JSON Lines is scanned without loading the whole source into one string. Forge stores every prepared dataset as ordered Arrow batches of at most 8,192 rows while retaining a row-oriented compatibility view for editing and filtering. Query or stream larger sources. Full-table CSV, TSV, JSON Lines, Parquet, and Arrow IPC exports stream those batches on the background worker; Forge writes a sibling temporary file, syncs it, and safely replaces an existing destination only after success. Runs can be compared, cloned, archived, and exported as ZIP bundles.

Every Forge build can choose **Tools → Import via Millwright** for CSV and Parquet. Forge embeds the published Millwright 2.2.1 crate, performs native loading on the background integration worker, then applies the same row, column, decoded-text, and cell budgets before inserting the result into the Arrow-backed workspace. No local Millwright repository is consulted.

Forge also embeds Burn 0.22.0-pre.3 with training, metrics, the portable Flex CPU backend, and WGPU. The Deep Learning pane can execute a native Burn tensor self-test and still generates editable Burn projects for longer-running training. CUDA and ROCm remain selectable for generated projects and remote jobs because bundling their platform SDKs into one cross-platform installer is not viable.

Remote execution profiles accept HTTPS Jupyter or JupyterHub base URLs; plain HTTP is restricted to localhost development servers. Tokens are stored in the OS credential manager and are passed to bounded requests without persistence in project files or placement in command-line arguments. **Test Jupyter** requests the server's kernelspec list with a 10-second timeout and 1 MiB response limit. Enter a discovered kernelspec name and use **Start kernel** to create one server-side kernel; Forge displays its server-issued ID and enables **Stop remote kernel** for explicit cleanup. The session is memory-only and Forge permits one managed remote kernel at a time. Enter code and choose **Run on remote kernel** to execute through an authenticated TLS WebSocket. Enable **Run notebook cells on active remote kernel** to route Run Cell, Run Above, and Run All through the same session; results and rich payloads return to the originating cell. Forge correlates messages to its request, collects text streams, tracebacks, and HTML, Markdown, SVG, PNG, or JSON MIME results, and completes only after both execute-reply and idle messages. Rich payloads are shown as inert source in a collapsible view rather than executed as active content. Jupyter input requests open a focused dialog; password requests are masked, replies are never persisted, prompts/replies are limited to 64 KiB, and unanswered prompts expire after five minutes. Cancel, the normal Stop action, and **Interrupt execution** use a separate control lane so they remain responsive even while execution or input is blocked. Remote code is limited to 1 MiB, combined returned text/rich output to 2 MiB, and reads to 30 seconds.

The SQL workbench accepts one read-only analytical statement at a time. It allows `SELECT`, `WITH`, `EXPLAIN`, `SHOW`, `DESCRIBE`, and `VALUES` forms while rejecting stacked statements and recognized mutation, DDL, transaction, locking, and `SELECT INTO` keywords before dispatch and inside connector execution. This lexical validation is a defense-in-depth usability guard, not a database security boundary: production profiles should still use database-enforced read-only accounts because vendor functions and extensions can have side effects. **Remove profile** removes the selected connection from project storage and then deletes its associated OS credential; if project persistence fails, Forge restores the in-memory profile and leaves the credential untouched. The workbench records statements only after a query returns successfully. History is scoped to the open project, deduplicated with the most recent occurrence retained, and bounded to 100 statements and 4 MiB. Select a recalled statement to return it to the editor, use **Export JSON** for a portable reviewable copy, or **Clear** to atomically replace the project history with an empty collection. Connection credentials and result datasets are never included in query-history files.

The training overview accepts framework-neutral `forge_training:` events from Millwright, Burn, or custom Rust training code. It validates finite scores, losses, metrics, and throughput; limits job, parameter, checkpoint, and failure text to 64 KiB; and retains the newest 10,000 events. The native run overview treats each `Started` event as the boundary of a sequential run, keeps legacy events before the first boundary in an unscoped run, and shows the newest 128 runs with status, trial and epoch progress, latest loss/metric, and best score. **Run summary CSV** atomically exports those analysis-ready run rows in newest-first order with ten stable columns, standards-compliant escaping, and a 16 MiB output limit. Interleaved concurrent telemetry requires separate streams because the current event protocol does not carry a run identifier on every event. **Open metric plots** converts available epoch/batch loss, epoch metric, completed-trial score, and batch-throughput events into native structured plots and switches to the Plots pane. Repeating the action refreshes same-name plots, which then participate in durable history and every JSON, SVG, PNG, PDF, and HTML export. **HTML report** creates a self-contained offline summary of epoch/batch/trial/failure counts, latest loss and metric, best score, and a bounded newest-1,000-event audit table. Report telemetry is escaped, individual details are limited to 8,192 characters, and the document loads no script or remote resource. **PDF report** creates a paginated native text report with the same summary and a print-oriented newest-500-event audit limited to 512 characters per event; Forge publishes it through an atomic rollback-safe temporary file. **Training bundle** creates an atomically published compressed ZIP containing typed JSON, CSV, the HTML report, re-importable native plot JSON, and a manifest with Forge version, counts, sizes, and per-entry SHA-256 digests; uncompressed content is capped at 192 MiB. **Import bundle** accepts files up to 100 MiB and verifies the exact entry set, expanded-size budget, manifest schema, aggregate and per-entry sizes, all SHA-256 digests, counts, and typed event/plot validation before replacing live events or refreshing same-name plots. **Export JSON** preserves the typed event stream, **Export CSV** writes an event index plus escaped event JSON, and both exports stop at 64 MiB. **Import JSON** reopens an exported stream using a 16 MiB input limit and replaces live telemetry only after every event passes validation. **Clear events** releases the live history. Training events remain memory-only unless explicitly exported or captured in an experiment artifact.

The deployment pane accepts `forge_service:` request/error/p95-latency events and `forge_drift:` feature-score/threshold events. Forge requires non-empty model/version/feature text of at most 256 bytes, finite non-negative latency and drift values, and error counts no greater than request counts. Each stream retains its newest 10,000 events. The native health overview selects the latest service event per model/version and latest drift result per feature, includes drift-only deployments, and shows requests, error rate/count, p95 latency, and feature breach/total counts for up to 128 deterministic model rows in a horizontally scrollable table. **Open monitoring plots** generates native request-volume, percentage error-rate, optional p95-latency, and feature-drift-with-threshold views, grouped by model/version/feature, then opens the Plots pane. Repeating the action refreshes same-name dashboards; each plot is limited to the first 128 deterministic series and inherits durable history plus every visual export. **HTML report** writes a self-contained offline summary of current service health, error rate, p95 latency, drift breaches, and the newest 500 events from each stream. Report fields are escaped, and the document loads no scripts or remote resources. **PDF report** creates a native paginated version with the same summary and bounded newest-500 service and drift audit sections, published through Forge's atomic rollback-safe PDF writer. **Monitoring bundle** atomically creates a compressed ZIP containing the validated JSON snapshot, offline HTML report, re-importable native plot JSON, and a manifest with Forge version, event/plot counts, sizes, and per-entry SHA-256 digests; uncompressed artifacts are capped at 64 MiB. **Import bundle** accepts archives up to 64 MiB and verifies the exact entry set, expanded-size budget, manifest schema and aggregate size, every artifact size and SHA-256 digest, snapshot validation, plot validation, and all event/plot counts before replacing live monitoring state or refreshing same-name plots. **Export CSV** atomically writes a combined service/drift audit with stable typed columns, RFC-compatible escaping, and a 16 MiB output limit. **Export snapshot** writes both streams in one versioned JSON document capped at 16 MiB; **Import snapshot** validates the full schema and all events before replacing live state, and **Clear monitoring** releases both streams. Monitoring remains memory-only unless explicitly exported.

The data grid renders only the rows and columns intersecting the viewport, with a small overscan buffer for smooth scrolling. This keeps very wide tables responsive without changing sorting, filtering, selection, editing, column visibility/widths, or linked plots. The footer reports how many visible columns are currently rendered. Filtering and sorting immutable datasets run on a coalescing background worker and results are accepted only when their dataset revision and query still match. Newer queries cancel stale scans at bounded checkpoints. Numeric and case-insensitive text sort keys are prepared once per matching row; mixed columns consistently use text ordering. The table briefly shows an indexing indicator instead of blocking input. Draft edits remain synchronously indexed so unsaved changes are reflected immediately. Extremely large datasets can still require substantial memory because the editable compatibility view retains decoded row strings; use a narrowed database query when full materialization is unnecessary.

The Data inspector includes a cached quality profile for each dataset revision: missing counts and percentages, numeric coverage, uniqueness, numeric range, mean, standard deviation, mixed-type and constant-column alerts, and Pearson correlations. Correlations are bounded to the first 10,000 rows and 24 usable numeric columns, sorted by absolute strength. EDA HTML exports include the same quality summary and strongest 20 pairs. File, SQL, and native Millwright imports construct their Arrow batches and prepare these profiles on the background integration worker before appearing in the workspace.

Forge reads an open table directly instead of cloning it for every frame. Filtered/sorted row indexes are cached until the filter, sort direction, sort column, or dataset revision changes. Runtime replacement, SQL reload, import, and committed edits create a new revision automatically. Draft editing deliberately bypasses the cache so filtering reflects unsaved cell changes immediately.

Inside the full data viewer, select individual or all filtered rows, hide or pin columns, and adjust each visible width. **Edit cells** creates a draft; **Save edits** replaces the in-memory table and rebuilds its Arrow batch, while **Cancel edits** discards every draft change. Selection export includes selected rows and visible columns. Choose numeric X/Y columns to create a linked scatter plot from the current selection.

Each table can produce a self-contained EDA HTML report or an offline PDF with dimensions, quality alerts, up to 500 column profiles, the strongest 20 correlations, and a 50-row by 20-column preview. Runs can produce HTML or PDF comparison reports containing final metrics, step counts, execution counts, tags, and Git commits. PDF creation is native and atomic: it needs no browser or Python runtime, synchronizes a sibling temporary file, and replaces an existing destination only after success. The compact built-in font supports printable ASCII; unsupported glyphs are shown as `?`.

New experiment runs use SHA-256 fingerprints for dataset contents, hashed source identities, the Cargo lockfile, and selected runtime package metadata. The experiment pane shows the algorithm and captured dataset count. Historical runs remain readable and are labeled as using legacy fingerprints; Forge does not silently rewrite their provenance.

File → **Export reproducible project bundle** creates a deterministic ZIP with a schema-2 manifest, file sizes, and SHA-256 content digests. It is limited to 20,000 files, 100 MB per file, and 500 MB total. Build directories, virtual environments, Forge state, Git state, symlinks, and credential-like files are excluded. Review the manifest before sharing.

The Plots pane accepts legacy metrics/vectors and versioned `forge_plot:` JSON. Structured plots and their order, series visibility, and log settings are restored at the next Forge launch; persisted history is limited to 128 validated plots and 16 MiB. Use the arrow buttons to reorder history and **Duplicate** to create an independently configurable copy with a collision-safe name. **Export plot history** writes the complete collection as one validated JSON file. Use **Import plot JSON** to load one exported plot or an array of plots; Forge validates the complete file before changing the view, applies the same limits, and replaces an existing plot with the same name. Structured plots support lines, scatter, bars, filled areas, 24-bin histograms, five-number box summaries, heatmaps, ROC, precision–recall, residuals, and feature importance. Each series can be hidden, axes can be transformed to log10, and definitions can be exported as JSON, standalone SVG, native 960×540 PNG or vector PDF, or self-contained interactive HTML. Log transforms, invalid-domain filtering, histogram bins, box summaries, and series visibility are applied consistently to visual exports. The HTML viewer provides series toggles, hover coordinates, wheel zoom, drag pan, and view reset without loading a CDN or other network resource. All visual exports run entirely inside Forge; raster and HTML canvas output enforce a 16-megapixel memory-safety limit.

## External tools and credentials

Forge invokes Cargo, Git, `gh`, Jupyter, Python, AWS CLI, rclone, DuckDB, PostgreSQL, or MySQL only for the feature that needs them. Those tools own their credentials. Forge project JSON contains profile metadata and opaque credential keys, never tokens or passwords.

## Database connections

The SQL inspector supports embedded SQLite plus the official DuckDB, PostgreSQL, and MySQL command-line clients. Save a project-scoped profile, then use **Test** before schema discovery or running a query. MySQL locations use `mysql://host[:port]/database`, with the username in its dedicated field; Forge rejects credentials and options embedded in that URL and requires the client to verify the server TLS identity. External database commands stop after 30 seconds, previews are limited to 10,000 rows and 64 MiB of delimited output, and stderr is scrubbed of the connection location and stored password before display.

Connection tests, schema discovery, and queries run on a background integration worker. Forge remains responsive while a request is active, temporarily disables conflicting integration actions, and opens successful schema/query results in the data viewer when the typed result returns. Query history is updated only after successful execution.

Enter PostgreSQL and MySQL passwords only in Forge's password field. Forge rejects passwords embedded in PostgreSQL URLs/keyword strings or MySQL URLs, stores accepted credentials through the operating-system credential manager, and never writes them to project profile JSON or command arguments. PostgreSQL uses `PGPASSWORD` and MySQL uses `MYSQL_PWD` only in the spawned client's environment. The optional ADBC integration exposes the common API boundary, while concrete ADBC driver-manager installation remains user-controlled.

## Object storage

The Storage inspector supports AWS S3-compatible buckets and configured rclone remotes without storing their credentials. Save a profile and use **Test** to verify that its bucket, prefix, endpoint, and external credential chain are reachable. Listings stop after 30 seconds and retain at most 4 MiB; the UI displays at most the requested bounded number of entries.

Tests, listings, and downloads use the same background integration worker as database operations, so slow networks do not block editor painting or input. Status text reports the queued operation and updates when the worker returns.

Download keys are relative to the profile prefix. Forge mirrors the full prefix and key beneath `.forge/object-cache/<profile>/`, so objects with the same basename do not collide. Transfers write to a temporary file, enforce a 2 GiB cache-object limit, and replace an existing cached object atomically. Failed, timed-out, or oversized transfers remove their partial files. Remote endpoints and common secret assignments are redacted from displayed command errors.

## Updates

Use Crates → Check signed updates. Forge downloads the small channel manifest, verifies its GitHub provenance attestation, and reports the matching platform artifact. It never installs or replaces the executable automatically.

## Diagnostics and privacy

Diagnostics are off by default. Settings can enable bounded local events and sanitized crash summaries for the open project. Forge never uploads them automatically. Use the explicit ZIP export to review the exact bundle before sharing it. See [Diagnostics and privacy](PRIVACY.md).
## Portable Millwright models and deployment

In Millwright Studio, build a pipeline and choose **Generate native Millwright ONNX export cell**. The generated Rust cell uses the published Millwright 2.2.1 crate, exports the fitted pipeline through `ExportOnnx`, reloads it with `InferenceModel`, and checks the prediction count. Add Millwright with its `onnx` feature to the notebook project before running the cell.

Use the Deploy inspector to register the resulting artifact, assign an alias such as `production`, and generate a Rust service. Forge resolves the alias first and copies that exact model version into the service. The generated service includes health, readiness, metadata, and prediction routes plus Docker, Compose, and Kubernetes templates. ONNX services perform real inference through Millwright 2.2.1 and accept `{"rows":[[...], ...]}`. Other registered formats receive a clearly labeled editable adapter.

Newly registered model versions are content-addressed with SHA-256 and cannot be overwritten with different bytes. Re-registering identical bytes is safe and idempotent. Forge verifies the artifact whenever it resolves a version or alias, and generated services repeat that verification during readiness and container health checks. The Deploy table shows artifact size and a short digest prefix; full hashes are retained in registry and service metadata.

Runtime output prefixed with `forge_service:` or `forge_drift:` and followed by JSON appears in the Deploy monitoring view. Service records can report `model`, `version`, `requests`, `errors`, and optional `p95_ms`; drift records report `model`, `version`, `feature`, `score`, and `threshold`.
